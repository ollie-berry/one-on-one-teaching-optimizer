# 场景资产建设与 Prompt 工程说明

本文件只在新建场景 Prompt、场景定义不完整或现有架构确实阻碍目标能力时读取。普通局部修改不以本文件的结构检查为重构目标。

新建任何场景 Prompt 前，应先完成场景定义，而不是直接写风格和话术。
## 1. 新学科或新模块立项清单

在写 Prompt 之前，先填写：

1. 学科与年级；
2. 模块在完整教学链路中的位置；
3. 学生进入前已掌握内容；
4. 本模块唯一核心职责；
5. 输入字段及其完整性要求；
6. 允许补充的信息范围；
7. 期望的学生目标状态；
8. 推荐教学主线；
9. 主要知识对象；
10. 适合的认知动作；
11. 学生“不知道”时的降难方式；
12. 典型错误状态及纠正方式；
13. 中间轮互动契约；
14. 结束轮契约；
15. 与前后模块的边界；
16. 可接受残留；
17. 明确不由 Prompt 兜底的问题。
## 2. Prompt 工程策略

适龄化模块应保持短小，只定义高价值原则。更具体的语言要求可分散到：

- 承接策略；
- 提问难度；
- 例子选择；
- 单轮长度；
- 禁止过度低幼。

## 3. 架构覆盖视角

架构服务控制，不是固定模板。新建或重构时，检查 Prompt 是否以适合当前任务的方式覆盖：

1. 角色与对象；
2. 场景职责、前置状态和停点；
3. 输入、知识来源与完整性边界；
4. 教学主线和推进原则；
5. 学生输入与累计证据处理；
6. 反馈、讲解、提问和节奏决策；
7. 轮次与结束契约；
8. 学生侧表达；
9. 少量底线和优先级。

这些是检查视角，不要求固定九段、固定顺序或统一标题。已有结构能够稳定控制目标能力时，应在原位置做最小充分修改。

## 4. 规则放置

把规则放到真正控制该行为的位置：

- 场景和停点问题进入场景职责；
- 覆盖与编造问题进入输入和知识边界；
- 学生状态不改变动作的问题进入学生输入与决策；
- 固定问式问题进入提问功能和触发条件；
- 结束轮问题进入轮次与产品契约；
- 表达问题若来自上游动作，应先修改动作机制，再处理学生侧语言。

不要把同一能力分散重复到多个章节，也不要把完整效果标签、评分表、历史 badcase 或其他学科规则写进 Teacher Prompt。

## 5. 允许结构调整的证据

只有以下情况才扩大到结构性调整：

- 多类问题持续指向同一上游结构；
- 局部修改无法改变实际控制机制；
- 核心规则明显冲突或彼此覆盖；
- 每修一个问题都会稳定损伤另一项能力；
- Prompt 需要不断增加例外才能维持；
- 关键规则被重复和低价值内容淹没；
- 固定流程使学生状态始终不能改变下一步。

重构重点是恢复清晰的场景职责、知识主线、学生状态决策、动作选择和停点，而不是让文本形式更整齐。

## 6. 新 Prompt 初版检查

按当前场景检查：

- 场景：模块为何存在、讲到哪里停、与前后模块如何分工；
- 知识：输入覆盖、事实来源、允许补充范围和禁止编造；
- 教学：是否形成理解路径，单轮负荷是否与知识关系和学生状态匹配；
- 学生输入：最近回答与累计证据是否改变下一步；
- 问题：是否有教学功能，是否避免答案泄露、自问自答和模板过拟合；
- 表达：是否适龄、自然且不暴露内部分析语言；
- 产品：结束轮、控制字段、格式、标签和长度是否正确。

完成初版只说明 Candidate 可进入测试，不代表新场景能力已经验证。
