# 评测执行与回归检查
### 3.1 确认当前场景

先确认：

- 学科；
- 模块；
- 教学阶段；
- 当前 Prompt 版本及其唯一内容身份；
- 本轮目标；
- 测试集范围；
- 对应场景规则；
- 使用的 Teacher 模型、student simulator、关键运行条件和控制字段；
- 是否存在入参、测试流程或其他运行环境特殊情况。

版本名不能代替内容身份。同一版本名对应不同 Prompt 内容时，不得将其结果合并为同一版本；内容身份可以通过受控文件、版本记录或校验值确认，不限定具体实现方式。
### 3.4 区分问题来源

每个问题都要先判断来源：

- prompt 问题；
- 场景定义缺失或不清；
- 运行环境或测试流程问题；
- 入参问题；
- student simulator 问题；
- 单个 case 偶发现象。

不能把非 prompt 问题直接归因给 teacher prompt。

### 3.5 判断问题影响与本轮处理必要性

判断问题是否破坏知识准确、阶段职责、教学主链路、学生输入承接或真实互动；同时判断修改收益是否大于潜在回归风险。影响程度的具体口径以教学效果判别规则为准。
## 6. 问题来源判断

### 6.1 不得默认归因于 Teacher Prompt 的情况

以下问题不得默认归因到 teacher prompt：

- 入参缺失、错误或与业务预期不一致；
- student simulator 输出异常；
- 当前 Prompt 版本不确定。

### 6.2 非 Prompt 来源和入参问题不由 Prompt 兜底

已经确认属于运行或测试流程异常、脚本异常或入参主线缺陷的 case，不应继续往 teacher Prompt 中增加防御性规则。

### 6.3 来源不确定时的处理

如果问题来源不确定，应标记为“需 PM 或相关负责人确认”，不得直接进入 Prompt 修改。

## 7. 回归检查

### 7.1 版本稳定性检查

版本比较前，应先确认 Baseline 与 Candidate 的唯一 Prompt 内容、输入集、Teacher 模型、student simulator、场景与规则版本、关键运行条件和输出控制信息。任一关键条件无法确认时，仍可描述可观察差异，但必须缩小因果结论。

每次修改后至少对照：

- 原核心问题是否稳定下降；
- 是否出现新的底线问题或高优先级问题；
- 输入知识覆盖是否下降；
- 提问是否由一种模板变成另一种模板；
- 风格增强是否导致低幼或冗长；
- 规则收紧是否导致讲解干瘪；
- 目标学科有效规则是否误伤其他学科。

多轮教学中，即使首轮输入相同，Teacher 输出的变化也可能改变 student simulator 的后续回答，因此“同一初始输入”不等于“同一学生轨迹”。可以比较两版形成了什么不同的可观察教学关系，但不能仅凭这种对照，把差异严格归因于某一条 Prompt 指令。需要判断具体控制机制时，应尽量固定关键学生回复，或至少保留完整轨迹与运行条件。

Teacher 文本是否自然推进或收束，与 `nextRound` 或同类控制信号是否正确，是两个可以分别评价的对象。控制字段缺失时可以判断文本停点，不能声称产品控制已经正确。

### 7.2 回归检查重点

每次修改后，应同时确认：

- 原核心问题是否在原 badcase 和相邻 case 中稳定下降；
- 新版本是否只改变了表层话术，而没有改善教学动作；
- 是否漏讲输入中的关键知识；
- 是否由一种固定模板替换成另一种固定模板；
- 是否因为规则收紧而导致讲解干瘪、问题过难或互动消失；
- 是否误伤其他学科、模块、轮次或学生状态下原本有效的能力。
### 8.2 复测时

- 同时验证目标问题和回归风险；
- 检查跨 case 稳定性；
- 区分系统性问题与偶发现象；
- 评估继续优化的收益是否高于风险；
- 确认目标问题的改善是否能够跨 case 稳定复现。
