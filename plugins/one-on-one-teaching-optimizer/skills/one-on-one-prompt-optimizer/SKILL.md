# 一对一教学 Prompt 修改

本 Skill 承接已经明确的修改目标、教学效果问题或参考效果，将其转成 Teacher Prompt 中真正发挥作用的控制规则，并在保护原有能力的前提下形成 Candidate。

## 职责边界

本 Skill 负责：

- 判断任务属于直接编辑、问题修复、参考迁移还是结构建设；
- 判断已明确的效果问题是否可能来自 Teacher Prompt；
- 定位单条规则、缺失机制、规则组合、优先级或结构根因；
- 将用户要求和已确认教学动作转译为 Prompt 控制；
- 选择最小充分的局部修改、关联调整或结构重构；
- 生成用户需要的完整 Candidate、局部修改、差异或方案；
- 设计与修改假设相对应的回归，并向效果评定 Skill 交接。

本 Skill 不负责从原始 Case 中首次发现或定义教学效果问题，不自行定义新的学科教学标准、业务边界或产品契约，也不把未测试的 Candidate 声称为已经改善。

是否接受、继续、回退、准出或写入长期资产，由用户、PM 或 Owner 最终确认；本 Skill 只提出有依据的建议。

原始 Case 审查和修改后的实际效果复核交给 `$one-on-one-effect-review`。

## 先判断任务模式

### 1. 直接局部修改

用户已明确指定规则、字段、行为或表达变化，目标和影响范围清楚时，直接定位相关内容、检查相邻冲突并修改。此模式不要求补做完整 Case 审查，也不重复询问“是否确认修改”。

开始至少需要当前 Prompt 的准确内容、明确修改要求，以及会被改动影响的变量、格式或业务边界。

### 2. 已知问题修复

效果问题已经由 `$one-on-one-effect-review`、用户或 Owner 定义，但 Prompt 根因和修法尚未确定。问题定义应足以看清：

- 学科、学段、模块和教学阶段；
- Case 中的关键证据；
- Teacher 破坏了什么教学动作；
- 对学生理解或教学链路造成什么损失；
- 哪些能力仍然成立并需要保护。

若只有“效果不好”“互动不足”“太模板化”等笼统感受，先交给 `$one-on-one-effect-review` 定义问题，不直接把感受写成 Prompt 规则。

进入本 Skill 不要求 Prompt 来源已经被确认；判断问题是否来自 Prompt 是本 Skill 归因阶段的职责。确认属于非 Prompt 来源后停止修改，并指出应返回的环节。

### 3. 参考能力迁移

用户明确认可另一 Prompt、历史版本或 Case 的某种效果时，可以直接把它作为本轮设计参考。开始至少需要目标 Prompt、参考材料、用户想迁移的效果和目标场景边界。

有可比输出时先继承已确认的效果 Gap；只有 Prompt 文本或用户评价时，可以提取机制并生成待验证 Candidate，但要把机制表述为设计判断，不能声称已经证明因果或改善。

### 4. 结构建设或重构

新场景 Prompt、场景定义不完整，或多类系统性问题共同指向架构失效时进入。先确认场景职责、输入、内容边界、停点和产品契约；不能为了形式更工整而重构。

## 归因与修改

先明确本轮要改变的能力、必须保护的能力和最大回归风险，再选择与任务复杂度匹配的分析深度。

复杂问题先重建与目标行为相关的 Prompt 正向执行逻辑，找到真正占优势的控制机制。Prompt 中已有正确原则，不等于它实际控制了输出；继续检查更具体的固定流程、硬约束、优先级、重复规则和规则组合是否覆盖它。

归因可以是当前最有解释力、可通过回归验证的机制假设，不伪装成已经证明的条款级唯一因果。说明为什么修改这些位置，以及为什么暂时不动其他部分。

修改时：

- 追求最小充分修改，不追求字数最少；
- 先控制判断和教学动作，再处理学生侧措辞；
- 优先写正向决策机制，少量禁止项只守底线；
- 保留目标 Prompt 已有效的场景、知识、输入、输出和产品能力；
- 不把完整效果评定框架塞进 Teacher Prompt；
- 不为一个边缘 Case 增加全局重规则；
- 不把知识字段、学生证据、问题和轮次机械一一绑定；
- 不把参考 Prompt 当作新的主 Prompt；
- 只有现有架构确实阻碍目标能力时才扩大到重构。

涉及教学深度、知识来源、结束轮、产品字段或其他未确权边界时，指出具体分歧。若分歧会实质改变 Candidate，等待用户或 Owner 裁决；否则在已确认范围内继续，不设置机械确认门。

## 交付与验证

用户要求完整 Prompt 或需要可直接替换测试的版本时，提供完整 Markdown Candidate，并保留原有变量、input 字段、输出格式、JSON/XML/标签协议和未受影响的规则。用户只要求局部修改、差异或方案时，按其要求交付，不主动扩写整份 Prompt。

生成并交付 Candidate 可以完成本轮“Prompt 修改”任务，但不等于效果已经改善。只有用户要求验证、比较、确认效果或完成版本决策时，才继续执行对应回归；若尚无测试输出，交付可执行的验证设计即可停止。

回归应与修改假设对应：

- 典型原问题 Case 检查控制机制是否改变了教学动作，而不只是换了措辞；
- 相邻 Case 检查同一机制是否稳定；
- 历史有效 Case 检查保护能力；
- 高风险场景检查知识、边界、互动、表达和产品契约。

版本比较前，核对 Baseline 与 Candidate 的准确 Prompt 内容，以及会实质影响结果的输入集、Teacher 模型、student simulator、场景规则、运行条件和控制信息。条件不完整时可以描述可观察差异，但不能扩大因果结论。

测试次数、样本规模、通过阈值和显著性标准沿用用户、Owner 或业务已经确认的设置。当前资料没有规定时，可以列为待确定参数或本轮建议，不能写成项目既有硬规则。

需要实际效果复核时，将以下材料交给 `$one-on-one-effect-review`：

- 已确认的原效果问题及 Case 证据；
- Baseline 和 Candidate 的准确 Prompt 内容；
- 修改位置、控制机制和改善假设；
- 目标 Case、相邻 Case 和需要保护的历史能力；
- 适用场景规则和必要运行条件；
- 重点回归风险；
- 已生成的两版测试输出，如已有。

由效果评定 Skill 独立审查两版实际教学效果。没有复核结果时，只能说明修改已完成、Candidate 待验证，不能声称效果已改善或版本可以正式接受。

## 输出

只提供当前节点决策所需的信息。根据用户要求，可以包括：修改目标与保护项、来源判断、Prompt 控制根因、修改范围及理由、迁移映射、完整 Candidate 或差异、回归风险、验证设计和待确权事项。

关键结论应能回到用户要求、当前 Prompt、参考材料或 Case 证据，不强制固定报告模板。
