# 一对一教学 Prompt 优化 SOP

## 1. 定位

本文件是一对一教学 Prompt 优化的公共运行底座。它负责判断任务当前处于哪个节点、哪些结论应被继承、下一步应交给哪个能力；不替代教学效果标准、教学动作规则、场景规则或 Prompt 修改内核。

Prompt 优化不是单纯改写文字，而是对 Teacher 教学决策系统进行诊断、干预和验证：

```text
识别场景与目标
→ 观察当前效果
→ 定义问题并判断来源
→ 定位 Prompt 控制机制
→ 形成 Candidate
→ 测试与回归
→ 版本决策
```

这是一条默认路径，不是每次都必须从头执行的固定流水线。AI 应先识别用户当前所处节点，继承已经确认的上游判断，只补足当前任务真正缺少的部分。

## 2. 总体原则

### 2.1 标准化节点与交接，不机械标准化分析过程

允许根据用户已提供的信息、历史结论、任务复杂度和本轮要求跳过、合并或展开节点。不得为了展示流程而重复已经完成的效果审查、归因或确认。

### 2.2 先看效果，再看 Prompt

当任务来自实际教学表现时，优先依据测试结果、对应 input、学生输入和当前场景判断 Teacher 实际教成什么样；不要先读 Prompt，再猜它可能造成什么问题。

明确、局部、低风险的规则修改，以及用户已经确认目标效果的参考 Prompt 迁移，可以直接进入 Prompt 修改，但这只支持形成 Candidate，不自动证明效果改善。

### 2.3 先定义问题，再讨论修法

“互动不足”“反馈机械”“节奏不对”“不自然”只是体验描述。进入效果修复前，应尽量看清：

```text
学生当前状态
→ 此刻合理的下一步
→ Teacher 实际动作
→ 二者差异
→ 教学损失
```

### 2.4 问题成立不等于来源是 Prompt

来源可能是 Teacher Prompt、场景定义、input、student simulator、测试流程、运行环境、版本身份或单次随机波动。非 Prompt 问题不应通过向 Teacher Prompt 增加防御性规则来兜底。

### 2.5 每次修改同时定义“改变”与“保护”

Prompt 优化是在保护已有有效能力的前提下解决已明确问题。修改前至少应看清：

- 本轮主要改变什么；
- 哪些能力必须保持；
- 最少需要影响哪些模块；
- 最大的回归风险是什么。

### 2.6 badcase 改善不等于版本成功

单点测试只验证修改机制是否开始起作用。版本是否值得接受，还要看目标问题能否跨 Case 稳定下降、已有能力是否保留、是否出现更高优先级的新损失。

## 3. 七个运行节点

### 节点 1：任务理解

先确定本轮在优化什么。复杂任务至少要识别：

- 学科、学段、教学模块和当前阶段；
- 当前 Prompt 及其内容身份；
- 用户本轮目标；
- 可用证据与参考材料；
- 必须保留的能力、业务字段和产品契约。

场景按“学科 × 学段 × 教学模块 × 当前阶段”理解，不能只用学科名称代替。

若用户已经把对象、目标和边界说清楚，不单独输出任务定义，直接进入当前节点。

### 节点 2：当前效果诊断

证据优先使用：

```text
测试结果 + 对应 input + 当前场景
```

必要时再结合当前 Prompt。观察顺序遵循项目全局优先级：

```text
知识准确与内容边界
→ 阶段职责与停点
→ 教学推进
→ 学生输入承接
→ 互动与提问
→ 表达自然度
→ 跨 Case 稳定性
```

输出应说明学生当时处于什么位置、Teacher 做了什么、为什么不适合、造成什么损失，而不是只统计问号、表扬词、句式或轮数。

### 节点 3：问题定义与来源判断

把体验问题转成可观察、可修改的问题，并单独判断来源。

可按需要轻量区分：

- 必须解决：明显破坏知识、边界或教学主线；
- 优先优化：稳定影响教学推进或课堂体验；
- 可观察：证据不足或影响较小；
- 可接受残留：继续修改的风险高于收益；
- 非 Prompt 问题：返回对应上游处理。

正式效果分级沿用效果评定资产，不在本 SOP 中另建标签体系。

### 节点 4：Prompt 归因

把已经明确的问题翻译成 Prompt 控制机制问题。重点不是找一句“写得不好”的话，而是解释当前 Prompt 正常执行时，哪条规则、缺失机制、规则组合、优先级或结构使模型稳定选择了当前行为。

Prompt 中已有正确原则，不代表它正在控制输出。需要继续检查是否有更具体的固定流程、硬约束、重复规则或行为出口覆盖了它。

若来源不是 Prompt，或证据不足以支持修改，停在该节点并说明下一步所需材料。

### 节点 5：方案与 Prompt 修改

常用路径有三种：

1. **直接局部修改**：用户已明确具体规则、字段或行为，且关联风险有限；
2. **问题修复**：效果问题已明确，需要先归因再做最小充分修改；
3. **参考能力迁移**：用户明确认可另一 Prompt 或版本的效果，需要提取机制并适配目标 Prompt。

参考迁移按以下关系处理：

```text
参考效果 Gap
→ 可能产生该效果的机制 Gap
→ 目标 Prompt 已有保护项
→ 可迁移 / 不迁移内容
→ 目标 Prompt 控制点
→ Candidate 与回归风险
```

迁移教学决策原则，不机械迁移固定话术、固定问题形式、固定轮数、固定知识拆分或学科专属规则。参考 Prompt 是能力来源，不取得对目标 Prompt 的整体优先级。

用户需要可直接测试的完整 Prompt 时，交付全量版本并保留变量、输入字段、输出格式、标签协议和未受影响的有效规则；用户只要求局部修改时，按其要求交付局部内容，不主动扩大范围。

### 节点 6：测试与回归

材料允许且需要低成本验证时，可先用最典型 Case 检查目标机制是否真正改变教学动作，而不只是换了措辞，再扩展到批量或分层 Case。若用户已经提供完整批量结果，直接在现有数据上完成目标与回归检查，不机械重做单点测试。

回归至少覆盖：

- 原问题 Case；
- 同一机制的相邻 Case；
- 需要保护的历史有效 Case；
- 容易触发知识、边界、互动、表达或产品契约风险的 Case。

比较 Baseline 与 Candidate 时，对齐准确 Prompt 内容、输入集、Teacher 模型、student simulator、场景规则、运行条件和控制字段。条件不完整时可以描述可观察差异，但要缩小因果结论。

### 节点 7：版本决策

版本决策回答的是继续修改的收益是否仍高于风险，而不是是否消灭了所有瑕疵。

- 建议接受：核心问题稳定下降，原有重要能力保留，没有新增明显高风险问题；
- 建议继续：方向有效但机制仍不稳定，或出现可修复的新系统性问题；
- 建议回退：收益很小，却带来更大的损失、复杂度或不稳定性；
- 建议观察：剩余问题轻微，进一步修改更可能过修复。

优化 Agent 和各 Skill 提供分析建议；是否接受、回退、准出或写入长期资产，由用户、PM 或 Owner 最终确认。

## 4. 四种常见入口

### 4.1 效果诊断

输入通常是当前 Prompt、测试结果和 input。先由效果评定能力定义问题；若用户同时要求优化，再把确认后的问题交给 Prompt 修改能力。

### 4.2 直接优化

输入是当前 Prompt 和已经明确的目标或修改要求。继承已有判断，不重新做完整效果审查；完成必要归因、关联冲突检查和 Candidate 交付。

### 4.3 参考 Prompt 迁移

输入是目标 Prompt，以及用户认可的参考 Prompt、版本或效果。比较效果与机制，明确迁移边界、目标保护项和控制点，再形成适配后的 Candidate。

用户认可只授权把参考效果当作本轮设计依据；没有对照测试时，不把参考规则表述为已证明的唯一原因，也不声称 Candidate 已改善。

### 4.4 回归检查

输入是新版测试结果，以及 Baseline、历史问题或保护能力。先独立判断两版效果，再比较目标收益、新问题和回归风险，最后提出版本建议。

## 5. Skill 分工与交接

### 5.1 效果评定 Skill

负责节点 2、节点 3 中的教学效果定义，以及节点 6 中对实际输出的独立效果复核。它不读取 Prompt 反推根因，也不提出 Prompt 修改方案。

### 5.2 Prompt 修改 Skill

负责节点 4、节点 5，以及节点 6 的验证设计。它可以判断已明确问题是否来自 Prompt，并形成 Candidate；不从原始 Case 中首次定义教学效果，也不自行声明实际改善。

### 5.3 交接最小信息

从效果评定交给 Prompt 修改时，尽量保留：

- 场景和阶段；
- 问题及最短 Case 证据；
- 被破坏的教学动作与损失；
- 仍然成立、需要保护的能力；
- 已知来源线索与不确定项。

从 Prompt 修改交回效果复核时，尽量保留：

- Baseline 与 Candidate 的准确内容；
- 修改位置、控制机制和改善假设；
- 原问题、相邻问题和历史保护 Case；
- 运行条件和重点回归风险。

## 6. 默认交付

按用户当前节点交付，不强制输出完整流程报告：

- 效果诊断：主要问题、代表证据、教学损失、适用范围；
- Prompt 归因：效果问题、控制根因、建议修改方向；
- 能力迁移：效果 Gap、机制 Gap、迁移边界、目标适配；
- Prompt 修改：可直接使用的完整 Prompt 或用户要求的局部修改；
- 回归检查：目标改善、新问题、回归风险、版本建议。

当当前节点已经完成且后续需要新的测试、材料或业务确权时停止，不用为了走完流程而继续模拟后续阶段。
